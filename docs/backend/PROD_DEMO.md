# Demo environment on production (owner runbook)

For showing the deployed site (`https://vroomacars.vercel.app`, project `vrooma-prod`) with everything populated. Nothing
here is needed for real customers; when the demo is over, follow "Switching the demo off".

## What you get
Migration `0042_demo_data.sql` (generated by `scripts/build-demo-migration.ts`, one file) puts all the mock data on the
project, on top of the schema (0001-0041):

| Part | Contents |
|---|---|
| Catalog | 2 cities, 3 showrooms, 2 workshops, 6 models, 9 variants and colours, 4 demo cars, service types, 9 certified used cars, price rules for every variant and city, 2 offers, banners, lead routing rules |
| Accounts | 9 demo accounts: buyer (Aditya), consultant (Dev Consultant), 5 more consultants, manager (Vivek), admin (Sanjay). No passwords, no real mailboxes |
| Activity | 29 leads (LD-D-xxxx), 7 bookings, tasks, 3 support chats, garage cars with service history, saved cars, 17 AI call-log rows, 28 call-log rows |
| Slots | `generate_slots()` for the next 14 days, so test drives and service can be booked straight away |

Everything is idempotent (running it again changes nothing) and **nothing is ever emailed or messaged**: the outbox worker
skips the nine demo addresses, every `example.com` address and the demo phone numbers.

## Apply it
From `D:\Vrooma`, with the production values in your shell only (see `ENVIRONMENTS.md` section 3):

```powershell
pnpm db:push --target prod --i-am-targeting-production --dry-run          # must list 0001 ... 0042
pnpm db:push --target prod --i-am-targeting-production --confirm-production=zdasktnbdjkjtoncojsy
npx supabase link --project-ref eobtzcwinjmimzisypca                        # re-link the CLI to DEV afterwards
```

If 0001-0041 are already applied, only 0042 is listed and applied. If a file fails, its transaction is rolled back and
nothing half-applied remains; fix and run it again.

## Switch the instant sign-in on (demo mode)
In Vercel, Project Settings, Environment Variables (Production), add both and redeploy:

| Variable | Value |
|---|---|
| `DEMO_LOGIN` | `true` (server gate: without it `/api/auth/demo-login` answers 404) |
| `NEXT_PUBLIC_DEMO_LOGIN` | `true` (only draws the four buttons on the sign-in screens) |

The sign-in page and the sign-in sheet then show **Demo mode: instant sign-in** with four buttons: Buyer, Consultant,
Manager, Admin. Each signs in as that demo account with one click and opens the matching console.

> **There is no passcode.** While `DEMO_LOGIN` is on, anyone who opens the site can sign in as the admin account (change
> prices, see all leads, change roles). Use it for the demo, then switch it off. Every use is recorded in `audit_log`
> (`DEMO_LOGIN`), the endpoint allows 20 sign-ins a minute per visitor, and `pnpm check:env` prints a warning while it is
> on in production.

## Supabase settings (project `vrooma-prod`)
- Authentication, URL Configuration: Site URL `https://vroomacars.vercel.app`; redirect URLs
  `https://vroomacars.vercel.app/auth/confirm` and `https://vroomacars.vercel.app/auth/callback`.
- Vault secrets `app_url` (`https://vroomacars.vercel.app`) and `cron_secret` (same value as `CRON_SECRET` in Vercel), then
  `select private.ensure_cron_jobs();` so the cron jobs call the deployed app.
- Real buyers sign in with an emailed code, so keep custom SMTP (Resend) configured under Authentication, Emails.

## Check it works (about 5 minutes)
1. Open the site: the home page, **New Cars**, a model page (on-road price teaser), **Certified Used**, **Offers**, **Showrooms**.
2. Sign in as **Buyer**: Dashboard shows an upcoming workshop booking, saved cars, support chats; Profile shows **My cars**; book a test drive and see free slots.
3. Sign in as **Consultant**: Lead Desk with demo leads; open `LD-D-0001` for the AI briefing; **Suggest next steps** on `LD-D-0003` proposes asking a manager.
4. Sign in as **Manager**: Used Stock with the price-band note in a car drawer.
5. Sign in as **Admin**: Overview, **AI activity** (the 17 demo calls plus anything you do live), **System health** (cron jobs show real run times a few minutes after the Vault step).

The demo screens are time-relative ("a lead 2 minutes old", "a booking in 20 hours"). If you apply the migration days before
the demo, re-time everything right before you present with this in the Supabase SQL editor:

```sql
select private.refresh_demo_activity();
```

It removes and re-creates only the demo rows (ids starting `5eed`) and touches nothing else.

## Switching the demo off
1. Vercel: delete `DEMO_LOGIN` and `NEXT_PUBLIC_DEMO_LOGIN`, redeploy (the buttons disappear, the route answers 404).
2. When real data begins, run `supabase/remove-demo-data.sql` once in the SQL editor. It deletes the demo activity, the nine
   demo accounts and the refresh function; it keeps the catalog, which you then replace with real models, prices and showrooms in the
   admin console. It is generated from the same source as the migration and is not a migration, so it never runs by itself.

## Regenerating the migration
`0042` is generated, never edited by hand. If you change `supabase/seed.sql`, `src/lib/demo-personas.ts` or
`scripts/seed-ai-demo.ts`, run `node --experimental-strip-types scripts/build-demo-migration.ts`; a test fails when the
committed file is stale. A migration that has already been applied to a project is never edited: ship further changes as
a new numbered migration.
