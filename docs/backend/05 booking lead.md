# PHASE 4: SLOTS, BOOKINGS, LEADS, SLA, CSV, OUTBOX

Prerequisite: Phase 3 accepted. This phase delivers the business problem of the brief: every enquiry reaches a named consultant within 5 minutes; real slots for test drives and service.

## 1. SLOTS AND BOOKING
- `GET /api/slots` (public client, cached 30 s) and the booking pages read real slots: test drive by showroom + demo car + date; service by workshop + service type + date with bay capacity. Taken or full slots are shown disabled, never hidden. Past slots and slots inside the lead-time window are excluded server-side. Timezone: slot days are IST days.
- Booking is a server action calling `book_slot` (idempotency key required). Success returns the booking `ref`, slot, showroom, consultant (display name only). On `VR001` (slot just taken) return a typed conflict and the UI refreshes the slot list with the existing toast. The booking also creates or attaches a LEAD (source `web`, status `test_drive_booked` for test drives; service bookings create a service lead) through `create_lead` so a named consultant is assigned in the same transaction.
- Cancel and reschedule: server actions calling `cancel_booking` / `reschedule_booking`; show the policy (window constant) in the UI; a cancelled slot becomes bookable again immediately; confirmation is sent through the outbox.
- A user may not hold two confirmed bookings of the same kind at overlapping times; the error is friendly and names the existing booking.
- The profile must be complete (`requireCompleteProfile`) and the "service contact" consent must exist before booking; otherwise route to onboarding and resume.
- Service booking collects the vehicle registration number: validate the Indian format, uppercase, store in `vehicle_info`, treat as personal data (never shown publicly, masked in staff lists, included in export and deletion).
- Slot generation job `generate_slots` runs daily; add an admin screen action "Generate slots" with a date range (max 60 days) and a dry-run count.

## 2. LEADS PIPELINE
Sources: web forms (enquiry, contact, trade-in, booking), chat (later), CSV portal imports, walk-in (staff creates). All go through `create_lead` (never direct inserts).
- **Public forms** (contact, enquiry from a signed-out visitor): route handler `POST /api/leads`: zod validation; consent checkbox required; honeypot field; per-IP and per-phone rate limiting via `private.hit_rate_limit` (return 429 with retry-after); optional CAPTCHA token verification if the user has enabled Turnstile (behind an env flag); the handler uses the admin client ONLY to call `create_lead`, never to bypass validation. Signed-in users use the server action with their own session.
- **Normalisation:** phone to E.164 (shared `lib/phone.ts`), email lower-case, name trimmed, message limited to 1000 chars with control characters removed.
- **Dedupe:** repeat enquiry for the same phone + model within 24 hours appends an event and re-notifies the assigned consultant instead of creating a second lead.
- **Assignment:** `assign_lead` (Phase 2). Rule order: exact (showroom, model) rule, then (showroom, any model), then the showroom's default pool; an empty or fully unavailable pool leaves the lead unassigned, flags it in the inbox with a red "Unassigned" state and notifies the manager.
- **SLA:** `sla_due_at = created_at + 5 minutes`; `first_contacted_at` is set the first time status leaves `new`; the staff UI timer reads the stored timestamps; `flag_sla_breaches` runs every minute (idempotent), writes the event and notifies the manager through the outbox. Business hours: leads created outside showroom hours still get the 5-minute due time but are marked `after_hours` so the dashboard metric can exclude or separate them (ask the user; default: include and show both numbers).
- **Acknowledgement:** on create, an outbox row (email now; WhatsApp/SMS templates stored with `channel` and shown in the staff "Message preview" until a provider is connected) tells the buyer which consultant will contact them.
- **Staff operations (server actions + realtime):** inbox list with filters/search/pagination, realtime updates through Supabase Realtime on `leads` (RLS applies to realtime; verify a consultant never receives another showroom's events and that the subscription is cleaned up on unmount), status changes (validated transitions), re-assign (to an active consultant of the same showroom pool, reason required, event logged), notes, "mark contacted", reply send (writes an outbox row, flagged if it contains discount words; the UI already blocks them, the server enforces the same list), lost reason.
- **Concurrency:** two consultants updating the same lead -> optimistic check on `status_changed_at`/`updated_at`; the second gets a conflict message with the fresh state.

## 3. CSV IMPORT (portal leads)
`POST /api/leads/import` (consultant+, multipart or JSON of parsed rows; keep the PapaParse preview on the client but RE-VALIDATE every row on the server). Limits: file <= 2 MB, <= 2,000 rows, UTF-8 (strip BOM), delimiter auto-detect, header names mapped case-insensitively with a visible mapping screen for unknown headers. Per row: normalise phone/email/name, required fields, model name matched to `models` (fuzzy, shown for confirmation), `source_ref` (portal lead id) for idempotent re-imports (unique per source), dedupe inside the file and against the DB (same 24 h rule), partial success (valid rows are imported, invalid rows returned with row number and reason, downloadable as an errors CSV), write a `csv_imports` summary row (file name, totals, who, when), run assignment for each created lead in a bounded loop (batch of 100 per transaction), and never block the request longer than the platform limit (for large files respond `202` and process in the background with a status endpoint). CSV injection: cells starting with `= + - @` are neutralised on EXPORT (prefix with `'`), and on import they are stored as plain text.

## 4. DAILY CSV EXPORT FOR THE DMS (`GET /api/export/daily-csv?date=`)
Admin session or `CRON_SECRET` bearer; IST day boundaries; streams bookings and leads (columns documented in docs/backend/EXPORT.md); every cell escaped for CSV injection; PII limited to what the DMS needs; response is `no-store`; an audit row records who exported.

## 5. OUTBOX WORKER (`/api/cron/outbox`, called every minute by pg_cron via pg_net with `CRON_SECRET`)
Claims a batch with `FOR UPDATE SKIP LOCKED`, marks `sending`, sends email through Resend (templates: lead acknowledgement, booking confirmation, cancellation, reschedule, SLA breach to manager, staff invite fallback), records success/failure, retries with exponential backoff (1, 5, 30 minutes) up to 5 attempts then `dead` with an alert on the admin dashboard, safe to run concurrently, idempotent through `idempotency_key`. Email content in the user's locale, plain and minimal, with a one-click unsubscribe link for marketing mail only. WhatsApp/SMS: leave the channel enum and templates; no provider calls in this phase.

## 6. ADMIN "LEAK" DASHBOARD
`get_leak_metrics` through a server action: % of leads first-contacted within 5 minutes, median first-response time, breached count, bookings per day, service call answer rate (from service leads), and the money estimate using the brief's own assumptions (constants in one file, shown with a footnote that they are assumptions). Date range validation; empty states; no heavy queries on every render (cache for 60 s per admin).

## 7. EDGE CASES TO PROVE (tests)
Concurrent booking of the last slot; same user double-clicks (idempotency returns the first result); booking cancelled twice; reschedule to a full slot; slot generated twice; booking at the lead-time boundary; DST-free but timezone-sensitive day boundaries (23:30 IST booking appears on the correct day); user without complete profile; user with an overlapping booking; lead flood from one phone (rate limit); duplicate lead; CSV with BOM, semicolons, blank rows, 2,001 rows, malformed phone, unknown model, duplicate rows, formula cells; consultant removed from the pool while holding leads (leads stay, become reassignable, manager alerted); two consultants edit one lead; breach job running twice; outbox crash mid-send (no duplicate email on retry); realtime subscription isolation by showroom.
